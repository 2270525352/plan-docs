# 规划工作流

## 顺序

先选择入口，再汇合到同一开发闭环：

```text
新项目：原话留存 → PM 需求访谈 → AS-IS=尚未实现
老项目：原话留存 → 只读扫描 → AS-IS 事实基线 → 确认保留/改变/新增
→ TO-BE 需求
→ AS-IS/TO-BE/GAP 差异
→ AI 可读需求
→ 产品及交互模块树
→ 架构与接口
→ 总任务
→ AI 分工
→ 确定性审计
→ 一次六代理开发就绪审查
→ 必要时一次定向复审
→ 自动模式门禁
→ 实际开发
→ 测试/反馈/checkpoint
→ 用实现证据校正文档
```

用户可暂停、返回上游或只调用一部分规划能力。不得因为用户说“继续”就把尚未确认的需求当作已冻结。

## 新旧项目入口

- `greenfield`：围绕用户意图正向建设；`ASIS-*` 明确记录尚未实现，`GAP-*` 表示从无到有。
- `brownfield/incremental`：默认老项目模式，只扫描本次目标影响的入口、模块、接口、数据、测试和部署链。
- `brownfield/full`：仅在用户明确要求全量接管、补齐文档或大规模重构时使用。

老项目不要求用户复述历史。代码和测试能证明的直接记录为 AS-IS；代码不能证明的产品意图、
现状与目标冲突、删除/兼容取舍再询问用户。代码现状不自动等于正确需求。

## 原话记录

使用 `U-001` 起的单调递增编号。记录格式：

```text
record_id: U-001
time:
source: user message / attachment / meeting transcript
context:
verbatim: |
  <逐字原话，保留空行、错字、语气和顺序>
```

- 同一条消息保持一个记录；只有用户明确把内容拆成独立要求时才拆分。
- 追加前读取文件末尾，计算下一个 ID，禁止复用或重排。
- 附件原文按原始字符写入；无法无损读取时先停止并报告。
- AI 的问题、解释、建议、查证、摘要或结论不得进入本文件。
- 对旧版无编号的原话，不修改旧内容；在 `需求追踪矩阵.md` 使用 `LEGACY-U-<日期>-<序号>` 外部映射。

## PM 式访谈

按风险和影响分批询问，不一次抛出无关问题。至少覆盖：

- 项目服务谁、在什么真实场景使用；
- 用户当前怎样解决、为什么现状不足；
- 核心价值与“不做什么”；
- P0/P1/P2 优先级；
- 主流程、失败流程、空状态、权限和边界；
- 数据来源、隐私、安全、合规和时效；
- 可观察、可测试、可量化的验收结果；
- 已知事实、AI 推断和用户待确认项。

主动指出自嗨功能、重复路径、不可验证表述和成本不成比例的方案，但把最终选择交给用户。

## 环境与分工确认

在正式任务拆分前展示推荐方案并确认：

```text
environment_id:
project_mode: greenfield / brownfield
brownfield_scope: not-applicable / incremental / full
scope_boundary:
ccb_installed: yes / no / unknown
available_ais: [Claude, Codex, OpenCode, single-ai-cli]
claude_prompt_mode: verified-goal / ordinary-prompt / not-selected
claude_capability_evidence: F-*
codex_or_ccb_prompt_mode: verified-goal / ordinary-prompt / not-selected
codex_or_ccb_capability_evidence: F-*
planning_owner:
coordinator:
merge_authority:
reviewer:
accept_recommended_roles: yes / modified / no
parallel_allowed: yes / no
git_policy: auto / confirm / disabled
codex_app_scheduled_review: yes / no
scheduled_review_stop_policy: disabled / after-2-green / user-managed
review_policy: development-ready
full_review_round_limit: 1
targeted_rereview_round_limit: 1
review_call_budget: 12
confirmed_by_user:
confirmed_at:
```

推荐值：

- 大型项目由 Claude 主持 PM 访谈、产品/UX/AI 提示词与总体架构讨论；
- Codex 负责复杂工程实现、API/数据/算法、测试、调试、性能和构建验证；
- 独立 Claude Reviewer 只报告需求偏离、遗漏、冲突和歧义；
- OpenCode 只领取边界清晰、低耦合的实现、测试或资料任务；
- 允许无文件冲突的并行；协调者拥有最终合并权。

## 阶段确认

每次阶段确认写入 `CURRENT_STATE.md` 和对应文档：

| 门 | 用户需要确认 | 未确认时允许 | 未确认时禁止 |
|---|---|---|---|
| 模式门 | 新/老项目、老项目扫描范围 | 只读探查 | 建立全量事实结论 |
| 需求门 | AI 可读需求与开放问题 | 继续讨论、草拟 | 冻结架构/任务 |
| 产品门 | 模块树、交互、原型范围 | 修订产品文档 | 正式拆执行任务 |
| 分工门 | 环境、负责人、并行、Git | 给出建议 | 分发任务 |
| 审查门 | 六代理结论和修订 | 修订、复审 | 自动模式 |
| 执行门 | 最终规划与分工 | 输出阻塞清单 | 生成最终执行提示词 |

用户一次回复同时解决多个问题时，不要只更新需求正文。按固定顺序同步：
`用户原话 → 环境/分工 → 开放问题 → CURRENT_STATE → 追踪矩阵`。环境的
`available_ais` 只写稳定枚举；工具版本、命令探测和能力证据放入 `F-*`。同步完成前不开始
下一批产品节点或任务。

## 停止条件

遇到以下情况停止向下游推进：

- 用户原话无法无损获取；
- 需求互相冲突且用户未决定；
- 验收标准无法判定；
- 架构需要未经授权的新依赖或外部系统；
- 任务范围无法避免文件/接口写入冲突；
- Reviewer 出现 RED 或未处理的 P0/P1 YELLOW；
- 完整审查、定向复审或 Reviewer 调用达到确认预算；不得自动追加轮次；
- 用户未确认最终规划、分工或 Git 策略。

P2 必须进入待办并说明影响，但默认不阻塞开发。只有用户明确升级优先级，或新的证据表明它会
阻塞开发、验收、安全或兼容性时，才可提升为 P0/P1。
