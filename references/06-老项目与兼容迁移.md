# 老项目事实恢复、差异规划与兼容迁移

## 先选择范围

- `incremental` 是默认模式：从用户当前目标出发，只读取受影响的入口、模块、调用方、接口、
  数据、测试、部署和相关文档。
- `full` 仅在用户明确要求全量接管、系统性补文档或大规模重构时使用。

不要因为仓库存在代码就自动做全仓扫描；也不要因为扫描范围有限就把未读取区域描述成已确认。

## 先只读理解

老项目先读取：

- 根规则、当前状态、README 和已有规划文档；
- 依赖/构建配置、入口、目录和主要模块；
- 数据模型、接口、测试、部署和 Git 状态；
- 现有 `docs/`、hooks、Claude settings 和自动化配置。

区分三类内容：

1. 代码或文档可直接证明的现状；
2. 用户明确确认的目标；
3. AI 推断或待核实事实。

第三类只能写入 `AI推断与事实查证.md` 或 `开放问题.md`。

## AS-IS / TO-BE / GAP

1. 把可直接证明的当前行为写入 `00-source/项目事实基线.md`，编号为 `ASIS-*`；
2. 把用户确认要保留、改变或新增的目标写成 `REQ-*`，不得用现有代码替代用户目标；
3. 在 `01-requirements/现状与目标差异.md` 建立 `GAP-*`：
   - `create`：当前没有，目标需要；
   - `modify`：当前行为与目标不同；
   - `preserve`：必须保留并由回归测试保护；
   - `migrate`：需要数据、接口或部署迁移；
   - `remove`：目标明确授权删除；
4. 每个 GAP 给出影响范围、开发结果、验收标准和 `TASK-*`；
5. 实现后用代码、测试和 checkpoint 把 GAP 更新为 `implemented` 或 `verified`。

现有代码与用户目标冲突时，记录冲突并询问用户；不得默认选择“代码就是需求”或“新原话覆盖兼容性”。

## 旧版 plan-docs 映射

旧输出不移动、不删除、不覆盖。新树使用引用或复制后确认的迁移方式：

| `docs/00-项目说明书.md` | `03-product/项目说明书.md` |

## 非破坏迁移步骤

1. 记录旧文件清单、hash 和 Git 状态；
2. 运行 bootstrap，只合并根协调文件；
3. 创建新目录和空白规范模板，不覆盖同名内容；
4. 建立 `LEGACY-*` 来源映射；
5. 把旧内容转写到新 AI 可读字段时标记“迁移草稿”，逐项让用户确认；
6. 确认后更新追踪矩阵；旧文件保持原位；
7. 禁止建立含混的双重事实来源：新索引明确旧文件为 `legacy/read-only`；
8. 迁移通过审查后再决定是否归档旧路径；未获授权不移动或删除。

## 原话兼容

不要为了补 `U-*` 编号修改旧原话。对旧段落生成外部稳定映射，例如：

```text
legacy_id: LEGACY-U-20260614-01
source_path: docs/用户原话.md
source_anchor: whole-file
content_hash: sha256:<64 lowercase hex>
mapped_requirements:
```

映射放在 `需求追踪矩阵.md`，不放进用户原话文件。当前确定性审计只接受项目内非 symlink
文件的 `whole-file` SHA-256；需要段落级映射时先保留为迁移草稿，不得用无法复算的自由文本
锚点冒充已验证来源。

## 旧 hooks/settings

- 不修改无法安全合并的自定义 hook；
- 不把现有 `core.hooksPath` 改为新路径；
- JSON settings 只追加去重后的 Plan Docs hook 条目；
- 冲突时保留原配置，记录手动串联步骤和门禁阻塞；
- 所有安装前备份应可识别、可恢复；卸载只删除 Plan Docs 自有项。
