# 六代理审查

## 隔离原则

六个代理分别在干净上下文中读取原始项目文档，不共享其他审查代理的结论，也不接收“预期答案”或已知缺陷提示。它们只能把各轮原始报告写入 `06-reviews/agents/<review_round>-<reviewer_id>.md` 或返回报告文本，不能修改用户原话、规划或代码。

## 分工

| 代理 | 审查范围 | 必须给出的证据 |
|---|---|---|
| A1 | 用户原话 ↔ AI 可读需求 | U/REQ 缺失或误读映射 |
| A2 | 遗漏、歧义、假设、验收 | Q/REQ 与不可判定标准 |
| A3 | 架构、接口、数据流、模块 | ADR/API/MOD 覆盖与断链 |
| A4 | 总任务、依赖、并行、文件冲突 | TASK、路径、锁、拓扑 |
| A5 | Claude/Codex/Reviewer/OpenCode 边界 | owner、禁止范围、职责冲突 |
| A6 | 测试、Git、反馈、自动化、停止条件 | TEST/FB/CP/automation/gate |

## 统一报告格式

使用唯一模板 [代理审查报告.md](../templates/fragments/代理审查报告.md)。每个 finding
必须以 `### REV-A1-001` 这类 Markdown 标题开始，标题下保留同值的 `finding_id`、
`severity`、`evidence`、`affected_ids`、`problem`、`required_resolution` 与 `status`
字段；审计脚本据此核对原始报告和汇总，不能改成自由文本或 YAML 列表。

分级：

- GREEN：范围完整、可追溯、无阻塞；
- YELLOW：存在缺口、假设或弱验证；标注 P0/P1/P2；
- RED：与原话冲突、需求/任务缺失、文件冲突、职责混淆或无法安全执行。

## 汇总与复审

协调者：

1. 收集六份原始报告；
2. 去重但保留所有 finding ID 和证据；
3. 把问题分配给相应规划文档，而非静默修复；
4. 更新 `审查汇总.md` 和 `CURRENT_STATE.md`；
5. 修订需求、产品、架构、任务或分工；
6. 对变更范围重新运行对应代理；涉及追踪链或并行计划时至少重跑 A1、A4、A6；
7. 保留前后审查记录，不覆盖旧结论。

## 自动模式门禁

门禁只有在以下条件全部满足时为 READY：

- 六个代理均有最新报告；
- 无 RED；
- 无未关闭的 P0/P1 YELLOW；
- 每个 REQ 有 TASK 和 acceptance；
- 每个 TASK 有 owner、范围、验证、测试、锁、反馈、停止条件；
- 写锁和接口锁无冲突；
- 分工与 Git 策略已确认；
- 用户确认最终规划和分工。

否则结论为 BLOCKED，并列出 `finding_id → owner → 修订文档 → 复审代理`。

## 并发降级

若平台不能并行六个代理：

1. 启动六次新的独立上下文；
2. 每次只给同一份审查提示词和一个 reviewer_id；
3. 清除上一次上下文或新建会话；
4. 直到六份报告齐全再汇总；
5. 在报告中记录 `context_isolation: degraded` 及原因。
