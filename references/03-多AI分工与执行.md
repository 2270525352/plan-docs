# 多 AI 分工与执行

## 角色边界

### Claude

- 主持需求访谈、PM 分析和实用性判断；
- 规划产品逻辑、UX、页面、交互和 AI 提示词；
- 参与总体架构讨论和文档编写；
- 可作为独立 Reviewer，但不得审查自己实现的任务。

### Codex

- 实现复杂代码、API、数据、算法和工程任务；
- 负责测试、调试、修复、受控重构、性能、构建和技术验证；
- 不自行改变需求、产品逻辑、页面设计、AI 提示词或已确认架构；
- 不用无依据硬编码绕过缺失的需求或接口。

### Reviewer（Claude）

- 使用独立、干净上下文；
- 检查需求对齐、遗漏、歧义、冲突和偏离；
- 默认只报告，不修改被审查文档或实现；
- 输出 GREEN、YELLOW、RED、严重级别、证据和建议。

### OpenCode

- 仅在用户选择后参与；
- 默认领取边界明确、低耦合的实现、测试或资料任务；
- 不假设支持 `/goal`；
- 最终职责由用户确认。

## 共同协作合同

每个任务声明：

```text
owner
coordinator
merge_authority
allowed_scope
forbidden_scope
write_lock
dependencies
shared_interfaces
input_contracts
output_contracts
expected_outputs
merge_order
conflict_resolution
stop_conditions
```

`shared_interfaces` 使用 `API-001:read`、`API-001:write` 这类“稳定 ID + 访问模式”。并行任务可以共同读取；只要任一方写同一接口，就必须建立依赖并按顺序执行。依赖任务的 `output_contracts` 必须与下游 `input_contracts` 至少有一个完全相同的稳定合同 ID。

协调者负责需求解释、锁分配、共享接口变更批准、合并顺序、审查闭环和最终 checkpoint。协调者不等于所有文件的唯一写入者。

## 模式 A：CCB 多 AI

- 先检测 CCB 是否安装和实际可用命令，不凭记忆构造。
- 从各 AI 任务文档生成 CCB 分发提示词；任务合同保持不变。
- 每个 agent 只领取其 owner 和 allowed_scope 匹配的任务。
- CCB 可并行调度不共享写锁且依赖已满足的任务。
- 返回结果必须包含实际文件、命令结果、假设、阻塞和建议合并顺序。
- 协调者在合并前检查接口、文件范围、测试和 git diff。

## 模式 B：无 CCB 多窗口

- 用 `CURRENT_STATE.md` 作为跨窗口状态与锁登记表。
- 每个窗口启动时读取根规则、当前状态和自己的任务文档。
- 窗口只在取得文件锁后写最终文件；其余窗口可只读研究或输出草稿到专属临时区域。
- 共享接口先由协调者冻结；消费者任务依赖其 checkpoint。
- 通过用户或协调窗口传递任务结果和 commit，不靠会话记忆。

## 模式 C：单 AI CLI 串行

- 使用同一份总任务和任务字段；
- 按依赖拓扑一次领取一个任务；
- 每个任务结束后完成验证、反馈和 checkpoint，再领取下一个；
- Reviewer 阶段使用新的干净 CLI 会话；若无法创建，明确降级为六次独立重启上下文。

## 并行安全检查

仅当全部为 PASS 时并行：

| 检查 | PASS 条件 |
|---|---|
| 文件 | `allowed_scope` 不重叠，或重叠路径明确只读 |
| 接口 | 不同时修改同一接口/schema |
| 依赖 | 所有前置 checkpoint 已存在 |
| 输入输出 | 上游格式与下游预期完全一致 |
| 写锁 | 每个最终文件只有一个 owner |
| 合并 | 顺序确定，冲突解决者确定 |
| Reviewer | 不实现被审查任务 |

不能证明安全时改为串行。

## 冲突处理

1. 双方停止写入冲突文件；
2. 在 `CURRENT_STATE.md` 标记锁冲突和受影响任务；
3. 保留双方提交/草稿，不互相覆盖；
4. 协调者对照用户原话、需求和接口契约决定合并策略；
5. 必要时新增上游任务，重新审查依赖与验收；
6. 记录处理结果和新的 checkpoint。
